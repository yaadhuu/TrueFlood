# TrueFlood — Architecture and Design Decisions

TrueFlood is a flood early-warning system. Sensor nodes report river and weather
readings; a backend decides an alert level for each node, stores the history,
shows it on a dashboard and sends WhatsApp/SMS alerts.

**The one idea to remember:** alarms come from simple, readable safety rules.
The machine-learning model only *advises*. That split exists because the model
was measured against a trivial baseline, and on the demo data it lost.

## The flow

```
 ESP32 sensor nodes (simulated in Wokwi)
   │  MQTT  flood/sensor/<node>   (a JSON reading every ~5 s)
   │  MQTT  flood/status/<node>   ("offline" Last Will when a node dies)
   ▼
 mqtt_client.py ──► nodes.process_reading() ──► predict.py
                                                  ├─ Layer 1  safety rules   → decides the alert level
                                                  ├─ Layer 2  Random Forest  → advisory forecast only
                                                  └─ Layer 3  weather API    → adds a reason, never overrides
                          │
                          ├─► db.py       SQLite: latest state + history per node
                          ├─► MQTT out    flood/alert/<node>
                          └─► alerts.py   WhatsApp → SMS fallback (if ALERT)

 app.py (Flask REST API) ──► frontend/index.html dashboard
                         ──► /api/health (for the host)   /api/metrics (Prometheus)

 Offline, separate:  USGS river gauge + Open-Meteo rain ──► train_real.py ──► MODEL_CARD_REAL.md
```

## The three decision layers (`predict.py`)

### Layer 1 — safety rules (decides every alarm)
Plain thresholds a person can read and argue with. Each rule that fires adds a
**reason** in plain words ("water level 3.40 m >= 3.0 m"), so every alert explains itself.

| Signal | WATCH | ALERT |
|---|---|---|
| Water level (0–4 m channel) | ≥ 2.0 m | ≥ 3.0 m |
| Rate of rise | ≥ 0.10 m/min | ≥ 0.25 m/min |
| 24 h rainfall | ≥ 90 mm | — |
| Pressure falling | ≥ 1 hPa/hr *with* humidity > 85% and rain started | ≥ 2.5 hPa/hr |
| Compound | — | water ≥ 2 m + rain ≥ 180 mm + soil ≥ 98% saturated |
| Forecast (Layer 3) | ≥ 90 mm forecast on soil ≥ 88% | — |

Why these signals:
- **Rate of rise** is the strongest flash-flood signal: a river rising fast matters even below the line.
- **Falling pressure** is the only signal that can fire *before* the water moves: a storm front arriving.
- **Compound rule**: high water, heavy rain and saturated ground are each survivable alone; together the next rain has nowhere to go but the river.

**Hysteresis (debounce).** A higher level must hold for 10 s before the node escalates,
and the node only stands down after 10 minutes clear. This stops one noisy reading
from flipping the alarm on and off.
**Corroboration bypass.** If two or more independent rules fire at once, escalate
immediately: a real flood shouldn't wait out a noise filter.

### Layer 2 — Random Forest (advisory only)
Predicts NORMAL / WATCH / ALERT and is shown on the dashboard, clearly labelled
"advisory". It never changes the alert level.

- **Training/serving skew fix.** The model was trained on *daily* rows, but sensors send
  a reading every ~5 seconds. Feeding 5-second packets into a feature called
  `rainfall_72h_mm` would be meaningless, so live packets are grouped into 60-second
  bins and one bin is treated as one training step. The *shape* of each feature matches training.
- **Out-of-distribution check.** Each input is compared with the min/max seen in
  training (stored in `model_card.json`); values outside are flagged.
- **If the model file is missing**, Layer 2 is skipped and Layer 1 still works. A
  missing model can never turn a flood into NORMAL.

### Layer 3 — weather forecast
Open-Meteo's forecast rain for each node's location, cached for an hour. It can
*add* a reason (forecast rain on wet ground → WATCH) but never removes one.

## The machine-learning story (the part interviewers dig into)

**Two datasets, on purpose.**
1. **Demo track** — synthetic data rescaled to the 0–4 m simulator range. It drives
   the live demo. Its label is a threshold rule over its own features, so there is
   nothing to *forecast*, only a rule to memorise.
2. **Real-data track** — 19 years (2006–2024) of daily data from USGS gauge 05389500
   (Mississippi River at McGregor, Iowa) plus Open-Meteo rainfall. The label is the
   **National Weather Service flood stage (16 ft)**, published by someone else, not
   tuned to this data. Task: will the river be in flood **2 days ahead**?

**Always compare against a baseline.** The persistence baseline says
"in 2 days it will be whatever it is today". It is one line of code and very hard
to beat on a slow river.

| Track | Random Forest | Persistence baseline | Result |
|---|---|---|---|
| Demo (macro-F1) | 0.46 | 0.71 | Model **loses** → it must not drive alarms |
| Real (flood-class F1) | **0.90** (recall 0.99, precision 0.83) | 0.85 | Model **wins by +0.05** |

**How it was evaluated.**
- **Blocked time-series cross-validation** (5 splits): each fold trains on the past and
  tests on the future. A random split would let the model peek at tomorrow.
- **Flood-class F1, not accuracy**: only ~5% of days are floods, so a model that always
  says "no flood" scores 95% accuracy and is useless.
- **Recall matters most**: a missed flood is worse than a false alarm, hence
  `class_weight="balanced"` and 99% recall.
- Random Forest settings: 400 trees, max depth 10, min 3 samples per leaf.
- 11 features: today's gauge height and yesterday's, 1- and 3-day change in height,
  today's and yesterday's rain, 3-, 7- and 14-day rain totals, temperature, and the
  distance to flood stage.

**Caveats to say before they ask.**
- Only 3 of the 5 folds were scored: floods cluster in time, so 2 early folds had no
  flood days at all (F1 is undefined there).
- The margin over persistence is modest because a big river moves slowly; most of the
  model's signal comes from current water level. Rainfall adds a little.
- The real-data model does **not** run in the live demo: simulator sliders can't
  produce Mississippi hydrology. It stands alone as a methodology check.

## Reliability and safety features

| Feature | Why |
|---|---|
| MQTT **Last Will** + 60 s timeout | A dead sensor looks exactly like a calm one unless you check. Stale nodes show **NO DATA**. |
| `/api/health` returns **503** when MQTT is down | So the hosting platform restarts a bridge that can't hear its sensors. |
| Alert **cooldown** (5 min/node) + **hourly budget** (all nodes) | Messages cost money; the budget bounds total spend however many nodes exist. |
| Dashboard alert needs a **key** + **allowlisted number** | Otherwise anyone could send messages from your Twilio account. |
| WhatsApp → **SMS fallback** | WhatsApp fails for boring reasons (sandbox expired) unrelated to the flood. |
| **Regional check** | Two live nodes elevated at once is a regional event; shown as context. |
| **Drift monitor** (PSI) | Warns when live data stops looking like training data. |
| Exactly **one worker** | The MQTT connection and per-node memory live in one process; two workers = duplicate alerts. |

## Likely interview questions

**Why not let the ML model fire alarms?** I measured it against a persistence baseline
and on the demo data it lost. A model that can't beat "assume nothing changes"
shouldn't drive a siren. Rules are auditable, and each alarm carries its reason.

**Why MQTT and not HTTP?** Sensors publish small messages often over unreliable networks.
MQTT is lightweight, publish/subscribe, and has a built-in Last Will that tells me when a node dies.

**Why Random Forest?** Tabular data, a few thousand rows, non-linear thresholds, and
feature importances I can explain. It is a strong default for this size of problem.

**What is the persistence baseline?** Predicting that the future equals today. On slow
rivers it is very strong, so beating it shows real skill.

**What's PSI?** Population Stability Index: compares the distribution of live data with
training data, bin by bin. Below 0.10 is stable; above 0.25 means a significant shift
and the model should be retrained.

**What would you improve?** Run the real-data model on a flashier river where persistence
is weaker; feed it hourly instead of daily data; move from SQLite to PostgreSQL for many
nodes; deploy on real sensors instead of the simulator.
